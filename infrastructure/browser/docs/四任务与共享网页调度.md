# 四任务与共享网页调度

任务状态和工作台按流程依次显示 **拉取、制卡、核验、修正**，各自启动或暂停。拉取保留可调并行菜单，可选32、54、72、85、100、120、150。制卡的网页设置只有 **最低并行**，默认 8，可选 1–20；制卡、核验、修正都显示 **实际并行**，不显示网页最大并行菜单。

最低并行保存在 `cards_min_pages`。`set_minimum(config, value)` 在控制写锁内设置下限，只将不足的制卡内部上限提高至该值，保留已有或并发设置的更高上限；降低最低并行不降低已有上限。CLI `python -m pipeline.concurrency_control --target cards_min_pages --value N` 使用同一接口。内部 `set_limit()` 继续严格校验上下限，原子成对设置可用 `set_limits()`。这些控制修改不恢复任何任务暂停。

为落实本轮共享 FIFO，制卡、核验、修正的旧独立上限一次性迁移为各 20，制卡最低并行为 8；全窗仍最多 20 页，不是各队分别 20 页。迁移保留前后记录及暂停指纹，不恢复任何暂停。此后不在轮询中强写 20；用户后续显式 CLI/API 上限调整继续生效，最低并行只抬高不足的制卡上限。

拉取不占用 GPT 页。其他三项复用已登记专用 Chrome 窗口的固定 20 个槽位。其他窗口页面不被接管、读取正文或关闭。最低并行是制卡的资源预留目标；实际并行由原会话生成状态决定，受待办、就绪材料、页面保护和 GPT 通道影响，不把预留或开页数显示成生成数。

实际并行只统计实时核对通过的请求：原 target 与唯一正式会话、材料标识和实际提示指纹一致，且新鲜页面观测确认仍在生成。暂停后仍在生成的原请求继续计数。未知提交、准备/上传、等锁和空白页面不冒充生成；没有足够的新鲜观测时显示 **待观测**，不沿用旧 `busy`、旧计数或补零。三项网页任务的实际并行与最低并行分别展示。

制卡默认预留至少 8 页，准备材料期间也保留空闲预留页；默认情况下，其余 12 页由制卡、核验、修正按入队时间共同排队。修改最低并行后，剩余页数随之改变。暂停制卡会让出其空闲页，活动页继续保留至完整收取。调高预留时不取消已有核验/修正，等空闲页逐步满足。未知提交、验证、故障归档中及有草稿的页面继续受保护，预留不足如实记录。

`shared_workflow_arrivals` 保存各任务不可变的 `queued_at` 和全局递增 `sequence`。新任务在数据库插入时登记，状态更新不改变顺序。旧任务无法恢复真实到达时间，以迁移登记时刻标注 `migration_registration`，不使用可变更新时间推断。调度先补制卡预留，再逐个合并剩余队列；所有者只按本轮 `claim_order` 的首项领取和串行上传/发送。材料准备在独立线程完成，不占生成页；活动/未知会话从原 target 收取，永不因换队或减少并行重新提交。

核验保存独立报告和分项评分。引文页定位、保持所有文字/数字/数学符号不变的排版建议及原文证据支持的重大重做，分别进入 `card_correction_jobs`，核验阶段不执行修改。引文定位和排版在本地处理；需要模型的重大重做使用 `kind=correction` 页和修正并行上限。旧卡片、原反馈、输入/回答指纹完整保留，每篇最多两次重大重做。修正后卡片仍 `scientific_verified=false`，新版本进入独立核验，不能把“修正完成”当作科学通过。

控制文件相互独立：

|任务|暂停文件|界面设置与观测|
|---|---|---|
|拉取|`fetch-control.json`|并行菜单 `fetch`，32、54、72、85、100、120、150|
|制卡|`web-card-control.json`|最低并行 `cards_min_pages`，1–20；实际并行|
|核验|`card-review-control.json`|实际并行|
|修正|`card-correction-control.json`|实际并行|

以上文件均在主 `data/`。`concurrency-control.json` 保存并行与预留。停止一项不停止其他已授权任务；仍有网页任务运行时，保留原共享驱动和观察器。全部网页任务停止后退出旧驱动。保持原三个 LaunchAgent，不新增常驻服务。`continuous_start --target all` 仍只启动拉取与制卡，避免连带恢复其他任务；独立核验/修正入口不新增网页或解除辅助 watcher 的用户暂停。
