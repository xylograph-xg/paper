# 制卡与核对共享专用窗口

2026-10-09，用户要求制卡和卡片核对共用一个专用网页窗口，保持20个固定网页，由检查程序分配任务，日常在其他窗口使用。授权原文见[本轮授权](../../../../paper/docs/authorizations/20261009-shared-gpt-window.md)。

## 窗口与页面归属

实施前只读盘点发现，专用浏览器 `127.0.0.1:9222` 中已有20个可证明属于本任务的实时页面，均在 `windowId=437808636`。登记直接沿用现存 target，不移动、关闭、清空这些页面，也不为登记另开20页。窗口 ID 是本次浏览器进程的运行标识，不是永久配置常量。

`data/shared-gpt-window.json` 保存专用窗口 ID，以及按 `01` 至 `20` 编号的固定槽位和各自 `target_id`。槽位保持稳定；目标消失时保留原 target，明确记为缺失，不把另一个空白页自动当作原页。登记缺失时只有主所有者可在实时归属和唯一窗口核对后登记；登记损坏、版本不支持或端口不一致时保留文件并等待核对，不能静默重建。

20页上限作用于登记的专用窗口。其他用户窗口的页面只用于浏览器元数据盘点及恢复保护，不读其 DOM、不导航、不上传、不发送、不关闭，也不计入本任务的工作槽位。未登记的网页即使在 ChatGPT 首页，也不因网址相同而被接管。专用窗口混入他人页面时暂停新增分配，保留各页面。

本任务已登记页面若移出专用窗口，不再领取新任务；其未收取原请求只在材料身份、提示指纹和正式会话证据核对后收取；已完成或空白页移出后仅保留元信息，不能以移窗、空白或 URL 变化为理由重发。

## 一个控制所有者

既有 `web_cards` keeper 是唯一 CDP 所有者，通过同一个连接管理制卡与独立科学核对队列。上传、设置和点击发送使用共享提交锁；网页生成可以并行。10秒观察程序运行在原连接事件循环中，检查受管页和需要保护的原会话，上传与提交锁等待期间继续观察。

`web-tab-watch` 保留本地库存补充、磁盘保留维护和收件箱发布。共享模式下，它只通过 HTTP `/json/list` 读取页面元数据、统计登记页，并写维护请求；不另连 CDP，不调用旧的补页、浏览器重启或历史关页路径。主所有者读取请求后核对登记和真实窗口状态，记录已经检查或请求已过期。

启动入口直接复用合法登记，不再搜索“全浏览器唯一空白 GPT 页”。显式启动发现尚未登记时，只写初始化请求供主所有者判断，不宣称窗口或网页已经创建。打开入口、写请求、调整并行均不解除持久暂停。

## 两种任务共享20槽

工作台和任务状态中的制卡、核对菜单仍分别设置各任务上限，保存用户当前选择，不强制改成固定的16路制卡和4路核对。两个上限不能相加后当作实际运行数。两队列都有可运行待办时，分配器在可用槽位内按各自上限分配共享预算；审核缺额优先获得释放的空闲页，制卡不能立即重新占满全部页。

例如，可工作的20页在上限20/4时预算为制卡16、核对4；上限20/20时为10/10。若上限6/10，且11页因未知回执受保护，剩余9页的预算为3/6。预算和实际活动数分别记录；页面可能仍在准备、等待额度、等待材料或等待原回答，因此20个固定页不代表20个正在生成的任务，更不代表20份完成结果。

已有生成或未知提交保持在原 target，不为平衡预算取消、搬迁或重发。减少并行只限制新分配，允许在途任务完成；固定页面不因菜单调小而关闭。核对独立暂停或某队列没有待办时，另一队列可使用符合自身上限的空闲槽；两队分别暂停，主所有者在任意一队获准运行时保持；暂停制卡不恢复核对暂停，也不阻止已独立获准的核对。未知提交、验证页、草稿和未完整收取的回答不参与新分配，也仍占物理槽位。

## 缺页与恢复

缺少固定页时，槽位保持缺失并等待明确核对。本机 Chrome 的协议清单及[CDP Target.createTarget 文档](https://chromedevtools.github.io/devtools-protocol/tot/Target/#method-createTarget)均没有指定既有 `windowId` 的参数；创建后页面可能进入用户正在使用的窗口。2026-10-09用户随后授权坏页自动检查及替换，新增临时MV3 worker按明确`windowId`后台补回一页；先归档原故障证据、关闭精确原target、确认其消失后才创建，随后卸载扩展。未知提交、无原归属的缺页继续保留，不能通过猜测活跃窗口补页；详见[坏页自动检查与替换](../../../../paper/docs/坏页自动检查与替换.md)。

旧 `browser_recovery.check_health`、`maintain_pool` 和旧关页路径在共享模式下不使用。CDP 连接断开时保留 Chrome、原页面、登记和账本，由原 keeper 重新连接并核对；本次不将重新连接称作已验收的 Chrome 关闭重启恢复。其他窗口存在时更不能为了本任务关闭整个浏览器。

## 记录与实现

| 文件 | 内容 |
|---|---|
| `config/first_round.json` 的 `web_cards.shared_window` | 开启共享窗口、固定20槽、缺页等待、登记窗口范围 |
| `data/shared-gpt-window.json` | 固定窗口和 target 登记；运行资源，不是授权或任务结果 |
| `data/shared-gpt-window-status.json` | 真实窗口观测、缺失/保护槽、两队列预算和派发状态 |
| `data/shared-window-maintenance-request.json` | watcher 或显式入口提出的 owner 维护请求及检查回执 |
| `data/gpt-window-pool.json` | 既有页面忙碌、就绪、待核对状态及原回答指纹 |
| `data/web-page-observer.json` | 每10秒真实检查时间、耗时、各页结果或错误 |
| `data/web-tab-check.json` | 登记池页数、浏览器总页数和其他页数的独立盘点 |
| `data/concurrency-control.json` | 用户选择的制卡、核对和拉取上限 |

窗口隔离在 `pipeline/shared_browser_window.py`，owner 登记和发送前窗口守卫在 `pipeline/shared_window_owner.py`，公平预算在 `pipeline/shared_page_dispatch.py`，两队列集成在 `pipeline/web_card_pool.py` 和 `pipeline/card_review_lane.py`。外围适配在 `pipeline/web_tab_watch.py` 和 `pipeline/web_pool_open.py`。

维护请求含 `schema_version`、`state`、`requested`、`origin`、`action`、`slot_count`、`ensure_page`、`manifest_sha256`，合法登记另含 `window_id`。`action=reconcile` 请求核对现存登记；`initialize` 仅由缺登记的显式启动入口提出。请求不构成新的材料发送授权。
