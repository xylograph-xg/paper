# 制卡与核对共享专用窗口授权

用户原文（2026-10-09）：

> 现在卡片核对和制卡都用网页，但是对网页控制有问题，能否二者共享一个专门的网页窗口，放置 20 个固定网页，检查程序进行分配，我平时打开其他的窗口来使用

本轮授权范围是主GPT制卡和已授权的独立原文核对共享一个专用窗口、20个固定网页及统一分配程序，避免干扰用户在其他窗口的日常使用。不增加独立审核浏览器、不恢复历史自动评审循环、本地模型、Qwen/DeepSeek或桌面App制卡。

实施前只读盘点：现有 `127.0.0.1:9222` 专用浏览器已有20个可证明属于本任务的实时页面，均在 `windowId=437808636`。直接登记现存 target 为固定槽位，不为登记新建、迁移、关闭或清空页面。窗口 ID 是本次真实运行观测，恢复后必须重新核对，不能把旧 ID 当作永久归属。

主 `web_cards` keeper 统一持有 CDP 连接，制卡和核对共享提交锁、10秒观察与20槽预算。外围检查程序只读 HTTP 页面元数据并向 owner 提出维护请求；启动入口复用登记。20页上限仅针对登记的专用窗口；其他用户窗口不读 DOM、不导航、不发送、不关闭，不纳入任务并行槽位。

制卡和核对菜单继续保留用户各自上限，两者按可用槽位共享预算，不把各20路解释成40个网页。减少并行不关固定页、不取消在途任务；未知提交和未完整收取的回答继续保护原 target，不重新发送。既有本任务原会话移出专窗时仅允许按原证据收取，不派发新请求。

缺失槽位保留原 target 并等待核对，损坏登记不静默重建。本机 `Target.createTarget` 没有指定既有 `windowId` 的参数，本轮实现不猜测用户活跃窗口来自动补页。共享模式不使用旧补页、Chrome关闭重启或关页路径；本轮不宣称这些操作已实测完成。

本轮改变浏览器资源组织与分配方式，不解除已有持久暂停、登录验证、额度等待或未知回执保护，不替代原文科学核对与生产合同验收。实现、记录文件和隔离测试范围见[制卡与核对共享专用窗口](../制卡与核对共享专用窗口.md)；原窗口及20个target保留、控制指纹不变和单所有者运行已核对，见说明中的验收快照；不把窗口验收当作科学核验。
