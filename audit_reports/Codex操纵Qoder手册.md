## 3. 如何根据需求选择工作区

- 对整体架构、项目间依赖、端到端流程、跨顶层项目的稳定性或安全性审查，选择 `paper`。
- 对单一子项目的代码、接口、可靠性或性能审查，选择该子项目，例如网页服务选 `workbench`，拉取选 `fetch`，制卡选 `cards`，核验选 `review`，修正选 `correction`。
- 同属一个物理父项目的多组件问题，优先选择该共同父项目。例如 browser/core/maintenance 的关联审查选择 `infrastructure`；reading/read/desktop_widget 与工作台的关联问题选择 `workbench`。
- 只有其他项目的必要公开接口用于验证局部结论时，仍在原子项目执行，并在 Prompt 列出允许只读核对的边界，不据此无限扩展为全仓审查。
- 工作区判断依据现有 `workspace.json`、`WORKFLOWS.md`、需求与当前源码，不创建空文件夹或第二份仓库。若需求确实无法确定范围，先检查现有项目结构；仍有关键歧义时再询问。

在发送前说明选择了哪个工作区及理由，避免问用户重复确认已明确授权的常规操作。

## 4. 确定的窗口操作方式

### 4.1 定位窗口与项目

1. 激活且只操作 `Qoder CN` 进程的目标窗口。
2. 从左侧边栏找到真实工作区；不在可见范围时滚动左侧项目列表，不滚动当前回答正文来寻找工作区。
3. 在目标工作区行最右侧悬停/点击，让加号显现，再点该加号新建会话。加号未悬停时可能不会出现在截图中，不据此认定入口不存在。
4. 重复建立三个独立新会话。不得使用已有用户任务会话，不向旧会话追加本次审查，不让三个编号共用一个会话。
5. 核对每个会话底部工作区名，并在 Prompt 中写入绝对项目路径。已有登记优先复用；工作区切换菜单仅作找不到边栏入口时的备用。

### 4.2 操作技术与定位原则

- 原生窗口操作可用 macOS 辅助功能（AppleScript/System Events）定位控件、读取属性、点击和向输入框赋值；截图用于核对真实界面。这是 App 操作，不是使用模型 API 或命令行代发任务。
- 可在需要时开启目标 Qoder 进程的 `AXManualAccessibility` / `AXEnhancedUserInterface` 辅助功能属性；这不代表模型设置已完成。
- 优先使用控件角色、名称、描述、工作区文本定位。控件结构随版本变化，不固定依赖深层索引。
- 坐标只是当次截图的辅助定位；窗口可能移动，Retina 截图像素与系统逻辑坐标可能不同。不得复用旧截图坐标盲点。
- 系统键盘事件发送到前台应用。每次输入或点击发送前重新核对目标进程、前台窗口与会话；用户切换前台时停止键盘输入并重新定位，避免把内容输入到其他 App。
- 向输入框设置 AX value 后，界面不一定触发编辑状态。需在正确输入框聚焦后触发一次真实编辑，随后核对全文和发送按钮状态。不得把“文本可见”当作已发送。
- 禁止通过其他应用/旧会话或服务端身份伪装绕过错误。不能把 API、命令行与 App 操作的结果混写。

### 4.3 每个会话发送前的核对清单

1. 工作区与绝对路径正确，编号为本批次唯一的 01/02/03。
2. 展开模型选项，明确选择 **Qwen3.8-Flash**；再检查 **极高** 强度，不能只看截断的模型按钮。
3. 展开权限选项，选择 **完全访问**，确认真实选中状态。
4. Prompt 全文与需求、审查范围、不覆盖规则一致，唯一标识及报告编号没有串号。
5. 目标目录存在且受 Git 排除；没有把三份报告指定为同一路径。
6. 当前会话无原有未发送草稿、无已发送的同一次任务；发送按钮确实可用。
7. 在正确窗口中只点击一次发送。观察新用户消息、任务标题/工具执行记录或明确发送回执，不以输入框变空单独判断成功。

## 5. 三份独立并行的含义

- 三份 Prompt 的审查问题、范围、证据标准和限制相同；仅批次/会话标识、编号与产物文件名不同。
- 不复制任何一次的回答、发现、评分、报告或旧审计结论作为另一次输入。不在 Prompt 透露其他两次的结论，也不要求凑满某个问题数量。
- 三个会话都自行读取当前规则与源码，不允许自行调用子代理或其他模型来替代三次独立执行。
- GUI 点击本身顺序发生，不能承诺物理意义上的同一毫秒发送。先完成三个会话的准备，再连续提交，使执行尽量重叠；记录三个实际提交时刻和运行状态。
- 如果第一个任务在另外两个提交前已经结束，或 Qoder 因额度/容量把任务串行排队，应如实标注“独立三次但未实际三并发”，不声称已满足同时执行，也不自动新增第四次审查。
- 每批只创建三个审查请求；明确发送前失败可修正后发送，已发送/归属未知不能重复发送。用户后续要求重试时另行记录。
- 用户操作其他会话不等于当前任务停止；只观察本批次三个会话，不干预他人的正在运行任务。

## 6. 只读边界与证据质量

每份 Prompt 都应明确：

- 先读当前工作区及父目录适用的 AGENTS.md、共享规则、README、interface.json；子目录有专门规则时按实际范围读取。
- 只读当前源码及必要公开接口；不给旧报告当答案模板，不把 README 描述当作已经验证的运行事实。
- 除最后以排他方式创建自己的 MD 报告，不写任何项目文件、临时脚本、配置、数据库、缓存、授权或回执；不调用会隐式写运行存储的业务接口。
- 不启动、重启、暂停或终止服务，不操作 Chrome/CDP，不发送文献，不运行真实业务，不提交/推送 Git，不安装依赖，不执行全局同步或自动修复。
- 仅可运行经核对不会修改项目/运行状态的读取命令；不运行测试、压测、导入业务模块或现场复现，除非用户另有明确授权。禁止读取凭据或输出密钥。
- 对“确定缺陷”“设计选择”“待验证风险”分别表述；每个问题给出当前文件路径、准确行号、触发条件、影响和建议。无法从当前证据证明时不补造。
- 不将用户要求的完全访问误解成允许放宽上述只读约束。项目暂停、未知请求、人工保护和原文/卡片保护始终保持。
- 若执行中发现源码被其他任务修改，记录开始/结束时能取得的版本与脏工作区状态，标记不可直接比较的范围。不得为了统一版本自行 stash/reset/切换分支、重命名或锁住他人文件。

## 7. 报告命名、独占创建与内容

规则见 [README](README.md)：

`项目名_调用模型名称_编号_MMDDHHmm.md`

本标准例：`workbench_Qwen3.8-Flash_01_10181605.md`、`workbench_Qwen3.8-Flash_02_10181605.md`、`workbench_Qwen3.8-Flash_03_10181605.md`。

时间由各会话在最终创建时按 Asia/Shanghai 获取，不虚构三者同一结束时刻。正文写完整日期与时间。编号与会话身份保持绑定。

必须使用 `open(path, 'x', encoding='utf-8')` 或 `O_CREAT|O_EXCL`。标准名冲突时保留原文件并追加 `_dup02`、`_dup03`，不改变会话编号。不得用 `write_text`、`open(...,'w')`、覆盖式重定向、追加写或编辑工具覆盖已有报告。

每份报告至少包含：

1. 批次唯一标识、会话编号、实际工作区、任务原始需求摘要。
2. 调用应用、实际模型/强度/权限（区分界面实见与任务指定），北京时间完整日期，版本与源码变化限制。
3. 审查范围、读取的规则和源码、只读方法。
4. 按严重程度列出的发现：文件路径/行号、源码证据、触发条件、影响、修复建议；无发现则明确说明。
5. 待验证风险、未执行的测试与现场验证、范围缺口。
6. 实际输出绝对路径及不覆盖写入方式。

即使受阻，也应在允许的只读与新建报告边界内保存一份明确写着“受阻/未完成”的报告；但若模型调用本身被拒绝或根本未执行，不能声称 Qoder 已生成报告。Codex 可另外新建明确署名为 Codex 的执行失败记录，不能冒用 Qwen 模型名或替代三份有效审计报告。

## 9. 观察、失败与停止

- 通过原会话工具执行记录、当前状态及最终回答观察进度；文件存在检查可直接从本机只读完成，不必反复切到前台。
- 尚在分析、排队或工具执行时，报告未创建是正常的待完成状态，不重发 Prompt。
- 报错时区分发送前失败、已发送明确失败、调用未知、额度、登录/权限。登录或验证码需要用户完成，不自动输入凭据或绕过校验；不擅自切模型。
- 保留原失败记录，不能把“工作中”或“文件卡片出现”当作成功，也不能把空白界面当作从未发送。
- 用户说“停止”时立即停止新点击、新输入、新任务和续发。若已有明确归属的本批审计正在运行，按用户停止范围请求 Qoder 的正常停止并核对；不强杀进程，不停止他人会话。不确定是否已停止时如实说明。

## 10. Codex 收取与验收

默认执行到三个独立会话确认发送成功即结束，不进入本节。只有用户另行要求读取、汇总、核对或明确等待报告时，才逐份完成以下核对；结果收取成功与任务发送成功分别记录：

1. 核对原会话已结束且最终回答中的实际报告路径属于 `audit_reports`，没有沿用历史路径。
2. 从磁盘以 UTF-8 完整读取实际文件，核对批次标识、会话编号、项目、模型和需求，不只读取标题或文件名。
3. 核对报告编号互异、没有串号；确认文件非空、结构完整、包含证据及验证限制，不是占位文件或错误回执冒充审计。
4. 两次读取内容/大小/SHA-256，确认内容稳定；对仍写入中的报告继续等待，不替 Qoder 补写或润色原文。
5. 用 `git check-ignore` 确认目录与报告被忽略，`git ls-files -- audit_reports` 应无条目。不得为“忽略”而移除已跟踪的其他历史文件。
6. 核对可取得的独占创建回执。文件此前不存在和当前存在本身不能证明用了排他创建；无法核对时记录“排他方式仅有执行方声明”，不夸大证据。
7. 把“文件收取通过”与“发现已独立复核/修复完成”分开。三份一致不等于正确；冲突回到源码核对，不能用多数票替代证据。
8. 仅在用户要求结果收取时，提供三份报告链接及各会话实际结果、并发情况、读取结果和限制。不自动修复代码，也不默认再开一轮。

后续任务按本标准操作。用户2026-10-18进一步明确：执行不需要等待回答，发出成功即可。此条取代之前默认等待三份报告落盘的完成判据；不取消Prompt内必须生成报告的要求。


## 11. 发送成功即交付（当前默认）

1. 按用户需求生成Prompt，选择合适工作区，核对模型、极高强度与完全访问。
2. 在三个独立新会话连续发送01、02、03，不等待前一个回答。
3. 对每份仅核对发送回执：本次用户消息确实进入正确新会话，并出现明确任务执行/排队回执或工具记录。只有输入框变空不足以证明成功。
4. 三份均明确发送成功后，立即结束本轮并汇报工作区、实际模型与强度、01/02/03发送结果。可说明“报告由Qoder完成后写入audit_reports”；不得称报告已生成或审计已完成。
5. 不继续等待、轮询任务状态、检查报告落盘或自动读取回答；不建立额外监控/定时任务。用户后续要求读取时，再进入第10节。
6. 原Prompt仍要求各会话最终独立生成不覆盖的审计报告。默认交付时机改变不降低报告要求。
7. 发送失败或回执未知不能计入成功。保存已知结果并向用户说明，不自动重复已发送或未知请求、不因未收到回答重发。
